## 2026-09-20: Daylight/Darkmode for the Android launcher

The launcher (Setup / folder picker / log viewer / GeneralsOnline
account) had shipped dark-only since the launcher-ui-2026 rework —
`Theme.Material3.Dark` with one near-black palette in
`res/values/colors.xml`. The user-facing ask was an in-app
Daylight/Darkmode choice.

Why not `AppCompatDelegate.setDefaultNightMode()`: the app
deliberately has no `androidx.appcompat` dependency (every Activity
extends plain `android.app.Activity` — same reasoning as
`LocaleHelper`'s manual `attachBaseContext` language wrap), and
`AppCompatDelegate` is an appcompat class. So the override is done
with the platform mechanism directly:

- New `ThemeHelper` (mirror of `LocaleHelper`): a `ui_mode` int in the
  same `generalszh_setup` prefs (0=system/absent, 1=daylight, 2=dark),
  and a `wrap()` that overrides only the `UI_MODE_NIGHT_*` half of
  `Configuration.uiMode` via `createConfigurationContext()`.
- Every launcher Activity now calls
  `super.attachBaseContext(ThemeHelper.wrap(LocaleHelper.wrap(base)))`.
  `LocaleHelper` stays the outer wrap it always was (it snapshots the
  configuration it is given), so the language override keeps
  authority; ThemeHelper only touches the night half.
- The theme parent moved to `Theme.Material3.DayNight`, which keeps
  Material's internal widget shading (switch tracks, slider, ripples)
  coherent in both halves — a fixed-Dark parent over a light palette
  would not.
- Palette split: the original dark set moved verbatim to
  `res/values-night/colors.xml`; `values/` now carries the daylight
  palette (M3 baseline purple-40 primary, matching surface-container
  ladder, status colours retuned for a light ground). No Java or theme
  name changed — every consumer already read tokens through
  `UiKit.color()` / theme attributes, so both halves resolve by name.
- The per-mode bits that cannot live in the palette file:
  - `android:windowLightStatusBar` now points at a bool resource
    (`gzh_light_system_bars`, true in daylight).
  - `Theme.GeneralsZH.AlertDialog` (the plain
    `android.app.AlertDialog`s) has a light framework parent in
    `values/` and a dark parent re-declared in `values-night/` — the
    two parents cannot be swapped through an attribute. Every other
    item is identical; only the parent differs.
- UI: a "Theme" card (system / Daylight / Darkmode as a segmented
  row, current answer as the header value) at the top of Setup →
  Interface, above Language. Applying is `recreate()` — the same flow
  the language picker uses, and safe because every Activity re-wraps
  its base context in `attachBaseContext()`.
- Strings in all 13 launcher languages, including the Arabic/Farsi
  RTL locales; the card is start/end-relative like everything else.

The game surface (`GeneralsZHActivity`) is untouched: it keeps its
own fullscreen theme, and the palette files were already comments-only
to it.

Validation: XML well-formedness across all touched res files; visual
check of both palettes pending a device build (CI: Build Android).

## 2026-09-21: Six accent colours for the launcher

Follow-up to yesterday's Daylight/Darkmode work: an Interface →
Accent picker offering six highlight colours — the existing violet
plus blue, green, teal, orange and red — selectable independently of
the mode, both palettes per accent, all through the existing theme
machinery.

The mechanism is a **theme overlay**, and choosing it (rather than
more resource splits) is the load-bearing decision of the day:

- The dark-vs-light question is a *resource-selector* question —
  which half of `values`/`values-night` resolves — so it must be
  answered before any context exists (hence yesterday's
  `attachBaseContext` wrap). The accent question is a *theme* question:
  five Material 3 colour slots. `Theme.applyStyle(overlay, false)` in
  `onCreate()` — before `super.onCreate()`, before any view, dialog or
  colour read — folds an overlay into the activity's own theme and
  every later lookup sees it. No context wrapping, so the hundreds of
  existing `this`-based builder calls in SetupActivity needed zero
  call-site changes.
- One overlay per accent covers both modes: the overlays name palette
  colours, and `values-night` resolves the dark halves underneath.
  The default violet applies no overlay — the base theme already is
  that accent.
- What an accent owns: `colorPrimary`/`colorOnPrimary`/
  `colorPrimaryContainer`/`colorOnPrimaryContainer` (the M3 slots
  widgets actually read), plus the framework legacy `colorAccent`,
  `colorPrimaryDark` and `textColorHighlight`. It does NOT own the
  surface ladder, outlines, error or danger (tertiary) colours — those
  stay neutral per mode, deliberately: a red accent must not make the
  red danger semantics ambiguous, and re-deriving five neutral shades
  per accent would be six hand-tuned palettes instead of five accents.
- Java side: `UiKit` gained theme-attribute readers (`accentColor`,
  `accentContainer`, `accentOnContainer`, `accentRipple` — the ripple
  is computed as the accent at Material's 0x33 alpha, which also made
  the `gzh_ripple_primary` resource redundant and deletable) and every
  accent-tinted widget path moved to them. `chip()` grew a convention:
  a 0 colour role means "resolve through the theme" (accent text on
  the neutral wash). SetupActivity's nav pill, slider, text field and
  folder-picker icons read through the theme now. Material dialogs and
  segmented buttons follow automatically because they read the same
  slots from the overlaid theme.
- The swatch strip (inside the Theme card, under a divider) shows each
  accent as BOTH modes render it — daylight half as the dot, darkmode
  half as a small crescent below — because the palette halves differ
  and the picker must not lie. That is also why `ThemeHelper` carries
  literal preview hexes: a darkmode activity cannot resolve the
  daylight value of an overlayed colour resource without constructing
  a second Resources instance, and the swatches are the one place that
  needs both at once.
- Applying is `recreate()`, same as the mode row and the language
  picker. Strings in all 13 languages.

Deleted code while here: `gzh_ripple_primary` from both palette files
(every consumer now derives it from the theme attribute).

Validation: XML well-formedness (44 files) and palette-name parity
across values/values-night; Java brace/paren balance on all six touched
files. Device visual pass pending (CI: Build Android).

## 2026-09-21 (later): the accent now tints the whole interface

Follow-up review of the accent pass found the real gap: the overlays
re-pointed the accent roles, but every SURFACE slot in the base theme
(colorSurface, android:colorBackground/windowBackground,
colorSurfaceVariant) still named the default violet palette, and the
Java code read surfaces as colour resources (UiKit.color(this,
R.color.gzh_surface_container)) — so an accented activity kept its
walls and cards neutral-violet and only the buttons changed. The user
ask asked for exactly what was missing: pick an accent and the whole
interface follows, pale in daylight, muted-dark at night.

Three coordinated moves closed it:

- **The base theme now carries the full surface attribute set**
  (colorSurface, colorSurfaceContainer/Low/High/Highest,
  colorOutline/OutlineVariant, plus background/windowBackground and
  colorSurfaceVariant). All of these exist in Material 1.12.0 — the
  tonal-surface attrs landed in 1.5.0/1.7.0, verified against the
  1.12.0 attrs source — so no custom attrs were needed.
- **Each accent palette grew a full tinted ladder** (background,
  surface, four container steps, outline pair, secondary pair):
  daylight values are pale pastel washes of the hue (#F9F9FE-class),
  darkmode values are near-black washes carrying only a whisper of the
  hue (#0D0F14-class) — the same derivation the default violet pair
  already used, so contrast comes from the untouched neutral text
  roles. The overlays re-point all of them; tertiary/error/status stay
  neutral per mode on purpose.
- **Java surface reads moved to theme attributes** (UiKit
  .backgroundColor/.surfaceColor/.surfaceContainer*Color/
  .outlineVariantColor, each with the same fallback pattern as the
  accent readers) across all four activities and UiKit's own card,
  divider, list-row, icon-button and chip surfaces.

One real bug surfaced while wiring this: the two remaining plain
`android.app.AlertDialog`s (and the third in the log viewer) do NOT
inherit an activity theme overlay — their builder throws away the
activity's resolved theme attributes (ContextThemeWrapper.setTo
semantics). All four dialog sites converted to
`MaterialAlertDialogBuilder`, which was already a dependency; the
hand-rolled `Theme.GeneralsZH.AlertDialog` light/dark parent pair in
values(-night)/themes.xml, the `materialAlertDialogTheme` wiring and
the comment blocks around them are deleted — the Material dialog theme
picks up the overlaid palette by itself now, and `gzh_dialog_background`
simply resolves its colour through the (overlaid) dialog theme.

Also swept onto the theme-attribute path while there: the GPU/version
diagnostic chips (chip()'s 0-role convention) and the slider's inactive
track.

Validation: XML well-formedness across all touched res files (incl.
44+3 new), brace/paren balance on the five Java files, no remaining
R.color surface reads outside ThemeHelper's fallbacks. Device visual
pass pending (CI: Build Android).
