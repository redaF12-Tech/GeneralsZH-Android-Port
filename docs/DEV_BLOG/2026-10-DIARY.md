# Dev Blog -- October 2026

## 02/10/2026 -- the lobby that could never start, and the joiner nobody can name

Two new screenshots from the same live session, one per side. On the PC: the
"Mismatch Occurred" dialog from 30/09 (still against the 27/09 APK -- the fix on
this branch has not been built yet). On the phone: the hosted lobby
"[AF][Android] RedaF12 Test" with every PLAY GAME press ending in red:
"Player UFAli ske is not connected to Player Reda F12", both directions,
"Starting full mesh connectivity checks...", "Mesh is not fully connected yet!
Please try again soon". The second screenshot is the worse finding: the lobby
could not start a match at all.

**Found: the full-mesh connectivity check is unwinnable in this build, by
construction.** P2P transport (NetworkMesh, GameNetworkingSockets) is deferred
-- `m_pLobbyMesh` and `GetNetworkMesh()` are always null. When the server asks
every client for its connectivity map, the response body is compiled out
behind `GENERALS_ONLINE_ENABLE_P2P_TRANSPORT`
(OnlineServices_RoomsInterface.cpp), so every client -- this one, and the PC
peers it can never connect to -- answers with an *empty* map. The server
aggregates, always concludes `mesh_complete=false`, and reports both directed
pairs of every player as missing. That is exactly what the screenshot shows.
The host was retrying a check that cannot succeed. The two existing skips
(the StartPressed pre-check and the RoomsInterface report) had removed the
mesh *code* from the flow; nothing had removed the mesh *gate* from the start
path, and the gate was the only thing between PLAY GAME and the countdown.

**Fix (WOLGameSetupMenu.cpp, StartPressed):** when P2P transport is off, do
not send `SendData_StartFullMeshConnectivityCheck` at all; take the path its
own success branch takes in this configuration -- buttons disabled, the
auto-ready countdown cleared, the "game starts in N seconds" announcement, and
`StartCountdown()`. The countdown tick already ends in `SendData_StartGame()`,
the server broadcasts START_GAME to every client, and each client's registered
game-start callback launches the match -- no mesh involved anywhere. The
unwinnable check itself stays in the tree behind the same `#if` for a future
P2P-enabled build, and an `#error` guards the one combination (no mesh, no
countdown) that would leave the game with no start channel at all.

**The mismatch screenshot, re-examined with the deployed build in mind.** The
APK on the phone is from 302d854d (27/09), which already contains the 23/09
revision tag (47685d9f), and `s_logicCRCRevision` defaults to the tag -- so
this device signed its checksums, and the PC's dialog at the first checkpoint
means the PC joiner was signing raw: a 28/08 client. That raised the question
the 30/09 entry left open: can an Android *host* know its joiner's client
before the first checkpoint? Answer: no, and not because the parser is lazy.
`LobbyMemberEntry` carries UserID/DisplayName/IsReady/Port/Side/Color/Team/
StartingPosition/HasMap/SlotState/SlotIndex/Region -- no exe_crc, no version.
`JoinLobby` does not even *send* the joiner's exe_crc (preferred_port,
anticheat_id, has_map, password only), so the server cannot know it either.
The lobby's ExeCRC field is whatever the host posted at creation, which is why
layer-1 reads it correctly for Android-joins-PC and is structurally blind for
Android-hosts-PC. What the tree can do is already done (58f25dde): layer-2
adopts the peer's variant at the first live checkpoint, so this device stops
erroring and continues in the peer's form. The PC's dialog is the 28/08
client's own behaviour and is fixable only in that client -- the current
092226 build signs the tagged form and pairs cleanly with this port.

Practical consequence for the next live test: UFAli ske's PC needs the current
GeneralsOnline client; the phone's `match start:` trace line will then read
`exe_crc=524577083` for the match, and both sides should pass the first
checkpoint with identical simulations -- which the replay corpus says they are.

Structural check on the StartPressed edit: 42 insertions, 0 deletions, brace
balance 546/546 (HEAD 544/544), preprocessor balance 45/45 (HEAD 42/42) --
same method note as 30/09: diff the structure against the base, do not count
braces by eye.

## 02/10/2026 (2) -- "no toolchain": a path nobody typed

The third screenshot of the day was the same hosted lobby as this morning's,
with the same red mesh errors, so there was nothing new in it to read. The
request was one line -- fix the build error `no toolchain` -- and no build log
came with it. Reproduced the message instead, which turned out to be enough.

**Found: the presets spelled both toolchain files as a path built out of an
environment variable.**

```json
"CMAKE_TOOLCHAIN_FILE":           "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake"
"VCPKG_CHAINLOAD_TOOLCHAIN_FILE": "$env{ANDROID_NDK_HOME}/build/cmake/android.toolchain.cmake"
```

CMake expands an unset environment variable to the **empty string**. It does
not complain, and it does not skip the toolchain -- it hands the path
`/scripts/buildsystems/vcpkg.cmake` to the toolchain loader, which does not
exist, and the configure dies with:

```
CMake Error at .../CMakeDetermineSystem.cmake:165 (message):
  Could not find toolchain file:
   "/scripts/buildsystems/vcpkg.cmake"
```

Verified against CMake 4.4.3 by running that exact path: reproduced the error,
then confirmed the rewritten configure reaches the same point and names the
real cause. That leading slash is the tell. A path that starts at the root
filesystem and names a well-known subdirectory is a variable that expanded to
nothing -- the message is about the *absence of an export*, wearing the costume
of a *wrong path*, and "no toolchain" is a fair but useless summary of it.

The vcpkg half is the one that bites first, because `default-vcpkg` is
inherited by every desktop preset too, so an unexported `VCPKG_ROOT` broke
Linux and macOS configure the same way. The Android half is sneakier:
vcpkg's own `vcpkg.cmake` includes `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`
*unconditionally* (line 208, `if(VCPKG_CHAINLOAD_TOOLCHAIN_FILE)`), so an unset
`ANDROID_NDK_HOME` does not skip the NDK include either -- it includes
`/build/cmake/android.toolchain.cmake`, which is not a file, and fails with a
bare `include could not find load file`. Note that `ANDROID_NDK` was never
mentioned anywhere in the preset, only the one spelling.

**Fix, three files plus two new toolchain resolvers.** Resolution now happens
before the path is assembled, so a variable that is simply not set is not a
failure mode:

- `cmake/toolchains/vcpkg-toolchain.cmake` -- finds vcpkg via `VCPKG_ROOT`
  (CMake var), `$VCPKG_ROOT`, `$VCPKG_INSTALLATION_ROOT`, `~/vcpkg`,
  `/opt/vcpkg`; requires both `.vcpkg-root` and
  `scripts/buildsystems/vcpkg.cmake` before accepting a directory, so a
  folder that merely happens to be named `vcpkg` is not mistaken for one.
  Exports `VCPKG_ROOT` for vcpkg's own port builds, which are separate
  processes.
- `cmake/toolchains/android-ndk-toolchain.cmake` -- finds the NDK via
  `ANDROID_NDK` / `ANDROID_NDK_HOME` / `ANDROID_NDK_ROOT` (CMake variable, then
  environment variable), then the newest NDK under `$ANDROID_SDK_ROOT/ndk` and
  `$ANDROID_HOME/ndk`, version-sorted so 28.x beats 27.x. Exports all three
  spellings at the one resolved directory: CMake's own
  `android.toolchain.cmake` reads `ANDROID_NDK`/`ANDROID_NDK_ROOT`, vcpkg's
  port builds have been reported to need `ANDROID_NDK_ROOT`
  (microsoft/vcpkg#29947, #27564), and this project's `arm64-android` triplet
  documents `ANDROID_NDK_HOME`. Which one a given dependency happens to read
  should not be a question the build has to answer correctly by luck.
- `scripts/build/android/android-ndk-env.sh` -- the same lookup in shell, for
  the three scripts that need the NDK before CMake runs (to find
  `llvm-readelf`, `llvm-strip`, `libc++_shared.so`). They used to *require*
  `ANDROID_NDK_HOME` to be exported, which was wrong twice over: it made a
  correct machine look broken, and `package-android-zh.sh` runs standalone
  often enough that a build which worked minutes ago could fail there purely
  because the environment was not carried over.

Both CMake resolvers now print every location they searched and the one command
that fixes it, with unset variables labelled `(unset)` rather than expanding to
a bare comma. A missing toolchain is the most common way a new contributor loses
an afternoon, and the whole cost of it was that the error described a path
instead of a variable.

Worth noting what was *not* wrong: the NDK pin, the vcpkg pin, the triplets, the
preset's ABI/API level. The build system was configured correctly and reported
a missing environment variable in a way that looked like a missing file.

**Also fixed while in there:** `build-local-sandboxed.sh` hardcoded
`.../prebuilt/linux-x86_64/bin/llvm-strip`, so on any other host the strip step
died with "No such file or directory" *after* a build that had otherwise
succeeded. It now globs `prebuilt/*/bin/llvm-strip`, the same way the readelf
lookup a few lines above already did, and fails with a message naming the path
it searched. Same class of bug as the toolchain one: a hardcoded path standing
in for a lookup.

Verified: `bash -n` on all seven Android scripts; the shell resolver against a
synthetic SDK tree in four configurations (nothing set, two NDKs present,
explicit override, and an `ANDROID_NDK_HOME` pointing at a non-NDK directory --
the last one correctly falls through instead of trusting the variable); the
CMake resolvers against real CMake 4.4.3 for both the found and not-found
paths, including that the three exported NDK variables reach child processes;
`linux64-deploy` still resolves its toolchain through the shared
`default-vcpkg` change; `CMakePresets.json` parses as JSON. Not verified: a full
Android cross-compile, which needs an NDK and a JDK this environment has
neither of -- that is the user's build to run.

### Later the same day: the SDK cache that poisoned itself

Opening the PR surfaced a second, unrelated failure -- `Build Android` died
with "NDK toolchain file missing after install", in a step that runs *before*
any of the toolchain work above is reached. The run list showed a second
failure 32 minutes earlier on `5946ce95`, the parent commit, which settles
the question of cause: not this branch.

The cache is self-poisoning, and the gate is the reason. "Save Android SDK
cache" is conditioned on `always()` and publishes whatever is in
`/opt/android-sdk` when the job ends -- so a run that died *before* the
sdkmanager call (a checkout failure, a transient error on the cmdline-tools
zip, a cancelled job) saved an empty or partial tree under the very key the
next run looks up. That run then restores the entry, sees `cache-hit=true`,
and skips the install, which was gated on the cache-hit flag *alone*. With
the install skipped there is no step left that can put the NDK back, so the
broken cache is inherited and the identical failure repeats forever. A gate
that asks only "did I get a cache?" cannot distinguish a good one from a
poisoned one; the flag says a directory arrived, not that it arrived
complete.

The same reasoning as the `llvm-strip` fix above, one layer up: a boolean
standing in for a check. Here the boolean is not merely wrong, it is
unrecoverable, because the thing it gates is the only repair mechanism.

Fixed by checking the tree rather than the flag. A step after the restore
looks for the pinned NDK's toolchain file, and the install runs on a cache
miss *or* a cache that turns out to lack the NDK, so the poisoned entry
repairs itself on the next run. The save is gated on the same check taken
*after* the install -- folded into "Export Android SDK environment", the only
point where the tree is known good. Getting that ordering wrong is easy and
was the first thing tried: keying the save on the pre-install check reports a
cold cache as unusable after a perfectly good install, and the cache is then
never written at all.

All five paths were traced against the gate expressions as parsed out of the
YAML rather than reasoned about: cold cache installs and saves a good tree; a
poisoned cache hit reinstalls and overwrites it with a good one; a good cache
hit is used as-is; an install that fails saves nothing, in both the cold and
the poisoned case. That last row is the one that closes the loop -- it is
what stops the next failure from inheriting the same entry.

Verified: the workflow parses, and the five-path trace above. Not verified
here: the Android cross-compile itself, still no NDK and no JDK in this
environment. The re-run on the PR is the real check.

### What the CI run found, beyond the cache

Opening the PR to get the toolchain fix exercised is what surfaced the rest.
The desktop jobs had not actually run in days -- "Detect File Changes" skips
the build jobs on pushes that do not touch their paths, so main's last few
"green" GeneralsX CI runs compiled nothing at all. Three pre-existing breaks
were sitting behind that, none of them from this branch:

**`<vector>` behind an `#if __ANDROID__`** (fixed in 532ebae). The header had
been added inside the Android guard alongside the draw-category hooks, but the
file uses `std::vector` unconditionally from `Shape_Arabic` onward. Both Linux
Flatpak jobs died on it. The instructive part is why it survived: Android is
the only configuration whose guard let the header through, and Android was the
only platform still being built, so the platform the include was added *for*
was precisely the one that could not detect its absence. `<chrono>` stays
inside the guard -- its only user, `GxUiTimer`, really is Android-only.

**Two Zero Hour-only calls in shared `Core`** (fixed in 076f35f).
`GroupPanelCalibrateFollowOffset` and `GroupPanelFollowControlBar` live in
Zero Hour's own `GroupPanel.cpp`; the base game has no `GroupPanel.cpp` at all,
yet `ControlBar.cpp` is shared, so `generalsx` could not compile. Guarded with
`#if !RTS_GENERALS` -- the base game's own macro, already used elsewhere in
shared Core. Writing the base game's panel would be a feature port, not a fix.

**A signature, not a missing symbol** (same commit). Zero Hour declares
`isPassengerAllowedToFire( ObjectID id = INVALID_ID ) const`; the base game
declares it with no parameter. One shared call site cannot name both. Passing
nothing for the base game is correct there -- its container answers the
container-wide question, the closest equivalent it has -- rather than a
silently dropped check.

All three were found the same way: read the CI logs to the actual compiler
error, then check whether the offending code differs from `main`. Two of the
three were in files my branch never touches, and `git diff origin/main...HEAD`
on them came back empty, which is what makes "pre-existing" a measurement
rather than an assertion. The `<vector>` diagnosis was reproduced standalone --
the guarded arrangement fails on this file's first `std::vector` use exactly
as CI reported, and compiles once the header is hoisted out.

Worth stating plainly: `generalsxzh` passed on macOS while `generalsx` failed
on the same commit. That asymmetry is the tell -- a shared-core regression
would hit both. It localises to what the base game does not have.
